# Лабораторна робота №2

## 1. Які бувають NoSQL бази

NoSQL бази з'явилися тоді, коли реляційні таблиці стали занадто жорсткими або повільними для специфічних задач. Основні види:

1. Документні (MongoDB, CouchDB). Дані лежать у вигляді JSON/BSON документів з вкладеними об'єктами і масивами. Зручно, коли сутність має складну деревоподібну структуру і читається цілком.
2. Key-Value (Redis, Memcached). Сховище "ключ-значення". Працює дуже швидко прямо в оперативній пам'яті. Використовується для кешу, сесій і простих лічильників.
3. Колоночні або Wide-column (Cassandra, ScyllaDB, HBase). Дані зберігаються по стовпчиках, а не по рядках. Добре підходять для величезних об'ємів аналітики, логів чи часових рядів.
4. Графові (Neo4j). Зберігають вузли і зв'язки між ними. Зручно для соціальних мереж, рекомендацій і пошуку складних шляхів між об'єктами.

## 2. Аналіз предметної області

Предметна область: система управління навчальними курсами.

Чи варто все переносити в NoSQL? Ні, переносити все не можна.
Користувачі, ролі, записи студентів на курс, здачі завдань і журнал оцінок повинні залишатися в PostgreSQL. Тут критично важливі транзакції (ACID) і зовнішні ключі (Foreign Keys), щоб не було ситуацій, коли оцінка виставлена неіснуючому студенту або курс створився без викладача.

Що вигідно винести в NoSQL:

1. Каталог контенту курсів (курс -> модулі -> уроки). На сторінці перегляду курсу користувач майже завжди відкриває всю програму одразу. В SQL це три окремі таблиці (courses, modules, lessons), які треба збирати докупи. У документній базі (MongoDB) це один документ, який читається за один запит.
2. Лічильники переглядів і рейтинг популярності курсів. Якщо кожен перегляд записувати в PostgreSQL через UPDATE рядка в таблиці, база буде гальмувати під навантаженням через постійні блокування рядків. Тому такі швидкі операції винесено в Redis.

## 3. Реалізація в NoSQL (MongoDB та Redis)

Для зберігання програми курсу було обрано MongoDB, колекція `course_content`.

Один документ містить:

- id, назву, опис і категорію курсу;
- вкладений масив `modules`;
- кожен модуль має свій вкладений масив `lessons`.

Для швидких операцій було підключено Redis:

- Лічильник переглядів конкретного курсу збільшується командою `INCR course:views:<id>`.
- Рейтинг найпопулярніших курсів оновлюється в Sorted Set командою `ZINCRBY courses:popular 1 <id>`.
- Повний JSON курсу кешується за ключем `course:content:<id>` з TTL 1 година.

## 4. Реалізація того ж самого в SQL

У PostgreSQL ті самі дані зберігаються в нормалізованому вигляді у трьох таблицях: `courses`, `modules`, `lessons`.

Щоб отримати таку саму структуру, як у MongoDB, було написано SQL-запит з використанням функцій `jsonb_build_object` та `jsonb_agg` (файл `src/nosql/course-content.sql`). Запит бере курс, підтягує його модулі, всередині модулів підтягує уроки, сортує їх за позицією і повертає готовий JSON.

У бенчмарку перед запуском тестів стоїть перевірка `assert.deepEqual`, яка підтверджує, що PostgreSQL, MongoDB і Redis повертають абсолютно однаковий результат.

## 5. Порівняння швидкодії

Тестувалася операція вибірки повної програми одного курсу з усіма модулями та уроками.

Як проводився тест:

- Згенеровано 3 набори даних: 50, 200 та 500 курсів.
- Кожен курс має 8 модулів, кожен модуль — 10 уроків (на наборі у 500 курсів це 4 000 модулів і 40 000 уроків, тобто разом 44 500 записів у трьох таблицях SQL).
- Перед вимірюванням робиться warmup на 25 запитів, щоб прогрілися з'єднання і кеш.
- Для кожного розміру виконується по 300 запитів по різних ID курсів.
- Вимірювалися середній час (avg), медіана (p50), 95-й перцентиль (p95) і кількість операцій на секунду (ops/sec).

Результати вимірювань (середній час на один запит та пропускна здатність):

1. Набір 50 курсів (4 000 уроків):

- PostgreSQL (3 таблиці): 0.64 мс (1 550 зап/сек)
- MongoDB (1 документ): 0.34 мс (2 934 зап/сек) -> в 1.9 раза швидше за SQL
- Redis (RAM кеш): 0.17 мс (5 784 зап/сек) -> в 3.7 раза швидше за SQL

2. Набір 200 курсів (16 000 уроків):

- PostgreSQL (3 таблиці): 0.65 мс (1 530 зап/сек)
- MongoDB (1 документ): 0.32 мс (3 125 зап/сек) -> в 2.0 раза швидше за SQL
- Redis (RAM кеш): 0.16 мс (6 240 зап/сек) -> в 4.0 раза швидше за SQL

3. Набір 500 курсів (40 000 уроків):

- PostgreSQL (3 таблиці): 0.65 мс (1 547 зап/сек)
- MongoDB (1 документ): 0.33 мс (3 055 зап/сек) -> в 2.0 раза швидше за SQL
- Redis (RAM кеш): 0.17 мс (5 920 зап/сек) -> в 3.8 раза швидше за SQL

Висновки з цифр:

- MongoDB вдвічі швидша за PostgreSQL на читанні дерева курсу (~0.33 мс проти ~0.65 мс), бо читає один готовий документ, а не збирає дані з трьох таблиць.
- Redis у 4 рази швидший за PostgreSQL (~0.17 мс), бо дані читаються напряму з оперативної пам'яті за ключем.
- При збільшенні бази з 50 до 500 курсів час вибірки майже не змінюється, тому що в усіх базах пошук іде за індексованим первинним ключем (ID) і зовнішніми ключами з індексами.
- Водночас якщо потрібно оновити лише один конкретний урок, то в SQL це простий `UPDATE lessons WHERE id = ...`, а в MongoDB доведеться оновлювати елемент всередині вкладеного масиву.

Сирі результати збережені у `benchmark-results.json` та `benchmark-results.csv`.

## 6. NoSQL іншого типу (Redis)

Як NoSQL базу іншого типу було обрано Redis (key-value сховище).
Реалізовані базові запити (файл `scripts/redis-demo.js`):

- `INCR` — атомарне збільшення лічильника переглядів курсу;
- `EXPIRE` та `TTL` — встановлення та перевірка часу життя ключа;
- `ZINCRBY` та `ZRANGE` (з `REV` і `WITHSCORES`) — додавання балів у відсортовану множину для рейтингу популярних курсів та вибірка топ-5;
- `SET` (з `EX`) та `GET` — кешування JSON-документів курсу з часом життя.

## Висновок

Реляційна база (PostgreSQL) найкраще підходить для зв'язків з високими вимогами до цілісності даних (користувачі, оцінки, зарахування).
Документна база (MongoDB) ефективніша для читання вкладеного контенту, бо знімає навантаження від об'єднання кількох таблиць.
Key-value база (Redis) незамінна для лічильників у реальному часі та кешу.
Використання декількох баз під різні задачі дає найкращу швидкодію застосунку.
